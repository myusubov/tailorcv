# GitHub Project Structure Analyzer

> Implemented path-only analyzer that summarizes repository shape, infers early stack/tool signals, and detects meaningful repository areas.

---

## 1. Core Philosophy

- Use deterministic path evidence before reading file contents.
- Keep stack inference conservative: structure-inferred stack is not the final source of truth.
- Emit evidence-backed areas that future analyzers can use as a cheap map.

---

## 2. Architecture Overview

```mermaid
flowchart TD
  Input[AnalyzeProjectStructureInput] --> Summary[buildProjectStructureSummary]
  Summary --> Shape[detectProjectShape]
  Summary --> Stack[detectPrimaryStack]
  Summary --> Languages[detectLanguages]
  Summary --> Manifests[detectRootManifests]
  Summary --> Areas[buildDetectedAreas]
  Shape --> Result[ProjectStructureAnalysisResult]
  Stack --> Result
  Languages --> Result
  Manifests --> Result
  Areas --> Result
  Result --> Future[Future analyzers and evidence aggregator]
```

The analyzer accepts already-fetched data:

- repository identity: `id`, `repositoryFullName`
- normalized tree entries: `path`, `name`, `type`, `depth`, `parentPath`, `extension` (lowercased at normalization), `sizeBytes`
- GitHub tree truncation flag: `isTruncated`

The analyzer does not fetch GitHub data, read file contents, or call AI.

## 6. Patterns & Conventions

### 6.1 Project Shape Detection

- **Rule**: Use score-based path evidence, not a single exact string match.
- **Rule**: Return `unknown` when evidence is weak.
- **Rule**: Keep possible shape scores private until there is a real consumer.
- **Rule**: Monorepo evidence includes common workspace config files such as `turbo.json`, `pnpm-workspace.yaml`, `nx.json`, `workspace.json`, `project.json`, and `lerna.json`, plus owner roots such as `apps/`, `packages/`, `libs/`, and weak `services/` evidence.
- **Rule**: Frontend monorepo paths should match generalized owners such as `apps/*/app` or `apps/*/pages`, not only `apps/frontend`.
- **Current labels**: `full-stack monorepo`, `monorepo`, `full-stack app`, `frontend app`, `backend api`, `library/package`, `cli tool`, `mobile app`, `documentation site`, `unknown`.

### 6.2 Inferred Stack Detection

- **Rule**: `summary.inferredStack` is structure-inferred only.
- **Rule**: Do not treat it as the final stack source of truth.
- **Rule**: Do not infer dependency-specific backend frameworks such as Express from generic folders alone. The detected-area Express.js detector only accepts conservative generator or layered API path clusters; dependency/config analysis should confirm package-level proof later.
- **Rule**: Path-only stack inference may include distinctive config or structure signals such as Next.js, Vite, Prisma, Docker, Turborepo, Nx, NestJS, Expo, React Native, native Android/iOS, and Flutter.
- **Rule**: Dependency/config analyzer will later confirm stack from files such as `package.json`, lockfiles, Prisma schema, Docker config, and framework config.

### 6.3 Language Detection

- **Rule**: `summary.detectedLanguages` is presence-only from file extensions -- no file counts and no primary-language ranking. Output is de-duplicated and sorted by name, matching `inferredStack`.
- **Rule**: The extension-to-language map in `language-detector.ts` keeps lowercase keys; lookups lowercase the entry extension defensively even though normalization already lowercases it.
- **Rule**: Keep the language union intentionally small (widely used languages); add new languages as demand appears rather than exhaustively up front.
- **Rule**: `.h` is always attributed to C; no vendored or generated directory exclusion is applied.

### 6.4 Root Manifest Detection

- **Rule**: `summary.rootManifests` records dependency manifests at the repository root (`depth === 0`) only, by presence and ecosystem, without reading file contents.
- **Rule**: Per-package manifests inside a monorepo are intentionally out of scope and left for the dependency/config analyzer.
- **Rule**: The manifest-filename-to-ecosystem map in `root-manifest-detector.ts` keeps lowercase keys; unmapped manifest filenames are ignored.

### 6.5 Detected Area Generation

> **Coverage note (2026-09-03):** the per-detector "confidence coverage uses ... fixtures through the public analyzer output" rules below describe fixtures that lived in `project-structure-analyzer.test.ts`, which was deleted. They record the intended fixture matrix, not tests that currently run, until that coverage is rebuilt (see Risks & Mitigations).

- **Rule**: `detectedAreas` identifies meaningful repository regions from path evidence only.
- **Rule**: Score concrete `(name, path)` candidates where `path` is the area owner root, not the individual evidence path.
- **Rule**: Evidence arrays must contain actual repository paths, not prose explanations.
- **Rule**: Root-level app or config evidence uses `path: "."`; monorepo app evidence uses owners such as `apps/frontend` or `apps/backend`.
- **Rule**: Every emitted detected area includes path-inferred technology metadata with one required `primary` technology and zero or more deduplicated `related` technologies. The primary is excluded from related values; internal candidates use a `Set` and public output converts it to a stable sorted array.
- **Rule**: `DetectedAreaTechnology` is composed from frontend, backend, containerization, runtime/platform, template, database, test, CI/CD, mobile, infrastructure-as-code, and documentation technology unions in `project-structure-analyzer.types.ts`; keep the public union stable while adding new labels to the narrow category that owns them.
- **Rule (amended 2026-09-24):** Candidates are keyed `${name}::${normalizePath(path)}::${primaryTech}`, so two detectors that claim the same area name and owner path with different primary technologies leave two separate candidates instead of one (previously the first detector owned `primary` and later score additions accumulated onto it). Score, evidence, and related technologies still accumulate per key. `reconcileCandidates` (`project-structure-reconcile-candidates.ts`) runs right after `applyDetectedAreaRules` in `buildDetectedAreas` and deletes a parent framework's candidate when a meta-framework candidate exists with the same area name and owner path. It is driven by the private `META_PARENT_PAIRS` table (area name, parent, list of metas): React under Next.js and React Router; Vue under Nuxt; Svelte under SvelteKit; React Native under Expo; Express.js under NestJS; native Android and native iOS each under Flutter, React Native, and Expo. Only an exact owner-path match competes; a parent on a nested path is kept. See [ADR 0005](adr/0005-same-owner-candidate-reconciliation.md).
- **Rule**: Reusable detected-area rule infrastructure such as `AreaRuleCandidate<Signal>`, owner candidate map creation, once-per-owner signal counting, and adding local owner candidates to the shared candidate map lives in `detected-area-rules/project-structure-area-rule-candidates.ts`; all active owner-scoped frontend detectors use it while still owning their signal unions, scores, finder variables, and output gates.
- **Rule**: The declarative engine (`detected-area-rules/declarative-area-rule-engine.ts`) resolves every signal's owner through the generic `ownerPathForApplicationArea` unless the detector passes an `ownerAdapter`. With an anchor-based adapter, the engine evaluates anchor schemas (`isAnchorSignal: true`) first, collects each anchor signal's resolved owner into an `anchorOwners` set, then resolves non-anchor signals against that completed set in a second pass; a detector with no anchor schema just has its adapter called once per matched entry. Seven adapters exist:
  - `detected-area-rules/owner-adapters/resolve-unit-root-owner.ts`, passed by sixteen detectors -- Next.js, Nuxt, Angular, Astro, React Router, SvelteKit (frontend); Django, ASP.NET Core, Laravel (backend); Prisma, Drizzle, SQLAlchemy, Sequelize, Knex (database); Jenkins (CI/CD); Docusaurus (documentation). Expo, React Native and Flutter (mobile) pass the sibling `resolve-native-platform-unit-root-owner.ts` instead (see below). An anchor signal is the framework or tool config file that sits at the unit root by that tool's contract (`next.config.*`, `nuxt.config.*`, `angular.json`, `astro.config.*`, `react-router.config.*`, `svelte.config.*`, `manage.py`, `*.csproj`, `artisan`, `prisma.config.*`, `drizzle.config.*`, `alembic.ini`, `.sequelizerc`, `knexfile.*`, `Jenkinsfile`, `docusaurus.config.*`, `expo-env.d.ts`, `app.config.(ts|js)`, and `react-native.config.js`); it resolves to the directory holding that file or bundle. A non-anchor signal resolves to the longest non-root `anchorOwners` entry that encloses it (a path with no directory segment resolves to `.`); when none does and `.` is an anchor owner it resolves to `.` (2026-10-07: a root anchor owns whatever no deeper anchor claims, including paths under `src` or an anchor-less `apps/<name>`); otherwise it falls back to `ownerPathForApplicationArea`, forwarding an optional per-call `extraRootDirectories` array when the caller passes one. Jenkins is one exception to "sits at the unit root": a `Jenkinsfile` can live at any depth (a root single-pipeline repo, or one per service in a multibranch monorepo), so every matched `Jenkinsfile` is itself an anchor and resolves to its own containing directory -- the only CI/CD provider that can emit more than one `CI/CD workflows` candidate per repository. Expo's third anchor, `expo-router-root-layout` (`app/_layout.*`), is a second exception: Expo Router requires a directory literally named `app` (or, since SDK 55's default template, `src/app`) to hold it, so the file sits one or two directories inside its actual project root rather than at it. The anchor branch special-cases this exact path shape by testing it against the same regex the entry schema uses, stripping the matched `app/_layout.*` suffix and any enclosing `src` segment instead of taking the plain dirname. Expo passes `extraRootDirectories: ['example']`, so a library repo's demo app (the `create-expo-module` convention, e.g. a nested `example/basic/eas.json`) resolves to `example/basic` rather than the repository root when no anchor nearby already claims it (a file directly under `example/` with no anchor, `example/eas.json`, resolves to its own path because `ownerPathForApplicationArea` returns `<root>/<second segment>` for a file as well as a directory; with an anchor in `example/` it resolves to `example`); React Native passes the identical `extraRootDirectories: ['example']` for the same convention in RN native-module library repos (react-native-webview and peers) -- `example` is not added to the shared `MONOREPO_OWNER_ROOT_DIRECTORIES` list since it is not a general monorepo convention every caller should inherit. React Native's own anchor, `react-native-cli-config` (`react-native.config.js`), sits at the unit root with no special stripping needed, unlike Expo's third anchor -- it reuses the adapter's original anchor-dirname behavior unchanged. `resolve-native-platform-unit-root-owner.ts` (2026-10-07) holds what Expo, React Native and Flutter need beyond this: when no anchor owner encloses a path, two further fallback branches run before the generic resolver -- a path containing an `android`/`ios` path segment resolves to everything before that segment, and a path ending in `metro.config.(js|cjs|mjs|ts)` resolves to its own immediate parent directory -- so React Native's non-anchor signals own bare example-app directories (e.g. `FabricExample/`) that carry no anchor of their own and are not nested under any workspace root `ownerPathForApplicationArea` recognizes. It never lets a root `.` anchor claim a path, because the library root would then win before those branches run (the `FabricExample/` case). Until 2026-10-07 both branches lived in `resolveUnitRootOwner` and ran for every caller. See [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md) (extended 2026-09-04, 2026-09-11, 2026-09-12, 2026-09-14, 2026-09-16, 2026-09-18, 2026-10-07).

The emitted candidate has primary technology `Ansible` and no related technology. | All five mobile providers are implemented (Expo, React Native (bare CLI), Flutter, native Android, native iOS -- the last two on 2026-09-19). React Native's `dynamicRelatedTechMap` adds `Expo` to `related` when the weaker `expo-modules-coexistence` evidence (`app.config.*`/`eas.json`) is present -- grounded in a rainbow-me/rainbow case study showing those weaker files appear on real bare-RN apps that individually install Expo SDK modules. An Expo owner that only React Native's gate clears (for example an Expo *bare workflow* app too weakly evidenced for Expo's own gate) surfaces as a plain `React Native` candidate with the Expo relationship lost, since there is no Expo candidate for `reconcileCandidates` to keep. Not observed in any sampled repository -- a documented, unobserved residual risk. Both Expo's and React Native's signal scores and gate shapes are research-stage (a ~90-repository GitHub code-search sample for Expo; the official RN CLI template plus six real production repos and a ~13k-hit code search for React Native), and neither has been cross-checked against Flutter, Android, or iOS. Flutter's own signal scores and gate shape are similarly research-stage: a GitHub-tree survey of 8 real Flutter repositories plus 2 plain-Dart negative controls (smaller than Expo's or React Native's sample), later widened for owner-resolution shapes specifically against `flutter/packages` (a 6-sibling federated plugin family) and `fluttercommunity/plus_plugins` (a melos workspace). Flutter shares no file-level signals with Expo or React Native, but its bundled Android and iOS hosts are structurally identical to a fully native app's, with no path-only signal to tell them apart. The native Android and iOS detectors close this from their own side (2026-09-24, replacing the 2026-09-19 anchor exclusions and `competingProofSchemas` veto): `resolveNearestMarkerOwner` redirects a bundled shell's owner to the nearest ancestor that directly holds a host marker, and `reconcileCandidates` drops the native candidate when a Flutter, React Native, or Expo candidate shares that owner. Residual risks of that design: (a) the walk does not require an `android`/`ios` segment, so any native anchor nested under a marker-holding directory resolves to that directory; (b) Capacitor, Ionic, and Cordova have no detector, so their redirected shells are not dropped, and Cordova has no marker at all (`config.xml` was deliberately left out as too generic), so its `platforms/android|ios` hosts surface as standalone native candidates; `app.config.(ts|js)` is also Nuxt 3's config filename, so a Nuxt project with a nested native app could be absorbed; (c) an `AndroidManifest.xml` cannot distinguish an application module from a library module by path, so a library module (confirmed on nowinandroid's `core/analytics`) resolves an owner and can clear the gate; (d) macOS/tvOS-only Xcode projects share the iOS shape; (e) NativeScript, .NET MAUI's modern layout, and Unity's export have no veto (documented conventions only, not repository-confirmed); (f) the Android and iOS research samples (8 and 9 real repositories) are smaller than Expo's or React Native's. Two additional residual risks surfaced during owner-resolution research, neither observed in a real repository: (1) a root-anchored Flutter app whose own top-level directory happened to be named exactly `apps`, `packages`, `libs`, `services`, or `modules` would misattribute a `flutter-macos-platform-dir`/`flutter-desktop-cmake`/`flutter-entrypoint`/`flutter-integration-test-dir` signal to `<name>/<child>` instead of `.`, since `resolveUnitRootOwner`'s `anchorOwners` set-membership check can never match a root (`'.'`) owner for any real path; (2) the opposite fix (letting `.` match unconditionally) was tried and rejected during this pass because it breaks an existing, real, confirmed test (`software-mansion/react-native-screens`' `FabricExample/` case) by short-circuiting the `android`/`ios` path-shape fallback before it can run -- no available fix resolves both directions of this ambiguity from path evidence alone. Same-owner reconciliation across providers is `reconcileCandidates` (2026-09-24); reconciling multiple claims across different owner paths in a monorepo remains deferred. | Revisit any mobile provider's gate/scores if broader sampling surfaces new false positives or cross-provider collisions. Extend `META_PARENT_PAIRS` when a new meta/parent relation appears. Revisit the root-owner `anchorOwners` ambiguity only if a real repository is found hitting either failure direction. |

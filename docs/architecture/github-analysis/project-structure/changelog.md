## 2026-10-07

### Docusaurus Detector

- **Problem:** The Docusaurus module in `detected-area-rules/documentation/` was an empty scaffold, so a repository documented with Docusaurus emitted no `Documentation` area. `docusaurus.config.*` is the site folder's required config, but in the research sample (2,413 repositories, 2,181 with a raw anchor) 17.4% of bare-anchor candidates (468 of 2,689 repo and folder pairs) were test fixtures, init templates, demos or the generated `.docusaurus/` cache, and the shared documentation blocklist alone would still have emitted 409 of them.
- **Solution:**
  1. Implemented `addDocusaurusDocumentationAreas` on `applyDeclarativeAreaDetector` with six signals: `docusaurus.config.[cm]?[jt]s` scores 3 (the anchor, marked `isAnchorSignal`, and the whole gate), and a sidebars file, `docs/**.md|mdx`, `blog/**.md|mdx`, `i18n/<locale>/docusaurus-plugin-content-*|docusaurus-theme-classic` and versioning (`versions.json`, `versioned_docs/`, `versioned_sidebars/`, optional `<id>_` prefix) score 1 each.
  2. Added `excludingDocusaurusNonDocumentationFolders` to `documentation/non-documentation-folders.ts` (shared list first, then `__fixtures__`, `__mocks__`, `templates?`, `create-docusaurus`, `samples?`, `playground`, `sandbox`, `starters?`, `e2e` and the `.docusaurus*` cache), and extracted a private `excludingWithExtraFolders` that it shares with the MkDocs builder; the MkDocs regex is unchanged.
  3. Wired `resolveUnitRootOwner` as the `ownerAdapter`, anchored on the config (it relies on the resolver change in the next entry).
  4. Added `'Docusaurus'` to `DocumentationDetectedAreaTechnology` and updated the dispatcher docblock.
  5. Added `resolve-unit-root-owner.docusaurus.test.ts` (owner spec from real layouts: facebook/docusaurus, jest, airbyte, typescript-eslint, nx-dotnet, mlflow, electron/website, authentik, Seeed-Studio). Expected owners were written from the layouts, not from the resolver's output, and were hand-computed; none was run.
- **Affected files:** `detected-area-rules/documentation/docusaurus-documentation-area-rules.ts`, `detected-area-rules/documentation/non-documentation-folders.ts`, `detected-area-rules/documentation/documentation-area-rules.ts` (docblock), `project-structure-analyzer.types.ts`, `detected-area-rules/owner-adapters/resolve-unit-root-owner.docusaurus.test.ts`.
- **Outcome:** A repository with a non-excluded `docusaurus.config.*` now emits a `Documentation` area with primary technology `Docusaurus` and related technology `React`, owned by the config folder (`.` for a root config). A support file that no config encloses (a repo-root `docs/` beside `website/`) adds nothing. Not verified: no test, typecheck or lint was run, no analyzer-level test covers Docusaurus or the exclusion regexes, and the signal contract comes from a search-biased sample with no held-out set.

### Native-Platform Owner Adapter and Root-Anchor Claim

- **Problem:** `resolveUnitRootOwner` ran React Native's `android`/`ios` and `metro.config.*` path-shape branches for every caller, so evidence such as `docs/ios/setup.md` resolved to `docs` for any detector. Separately, a repository-root anchor owner never enclosed a path (`.` is not a prefix of one), so a root Docusaurus site's `docs/src/intro.md` fell through to the generic `src` cut and resolved to `docs`, away from the site.
- **Solution:**
  1. Moved the two branches out of `resolveUnitRootOwner` into the new `resolve-native-platform-unit-root-owner.ts` (the resolver as it stood plus the two branches; a root `.` still never encloses a path). It is exported from the adapters barrel and passed by Expo, React Native and Flutter. The owner computation in both branches is collapsed to `parts.slice(0, i).join('/') || '.'`.
  2. In `resolveUnitRootOwner`, kept `.` out of the longest-owner comparison (it ties on string length with any one-character folder) and return `.` when no non-root owner encloses the path and `.` is an anchor owner, ahead of `ownerPathForApplicationArea`. Removed the redundant `size > 0` guard.
  3. Added `resolve-native-platform-unit-root-owner.test.ts`, added root-anchor cases to `resolve-unit-root-owner.test.ts` (root claims, a deeper anchor wins, the one-character-folder tie in both insertion orders, no-root fallback), and pointed the Expo, React Native and Flutter specs at the new adapter. Corrected the Expo docblock and README claim that `example/eas.json` resolves to `example` (a file directly under an extra root with no anchor resolves to its own path). Expected owners were written from the rule, not from the resolver's output.
  4. Added a 2026-10-07 update to [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md), which reverses its 2026-09-16 "every caller" decision and its 2026-09-18 rejection of `owner === '.'`.
- **Affected files:** `detected-area-rules/owner-adapters/resolve-native-platform-unit-root-owner.ts`, `detected-area-rules/owner-adapters/resolve-unit-root-owner.ts`, `detected-area-rules/owner-adapters/index.ts`, `detected-area-rules/mobile/expo-mobile-area-rules.ts`, `detected-area-rules/mobile/react-native-mobile-area-rules.ts`, `detected-area-rules/mobile/flutter-mobile-area-rules.ts`, and the specs `resolve-native-platform-unit-root-owner.test.ts`, `resolve-unit-root-owner.test.ts`, `resolve-unit-root-owner.expo.test.ts`, `resolve-unit-root-owner.react-native.test.ts`, `resolve-unit-root-owner.flutter.test.ts`.
- **Outcome:** Expo, React Native and Flutter resolve as before, and the other detectors no longer cut a path at an `android`/`ios` folder or a `metro.config.*` file. A root anchor now owns any path no deeper anchor encloses, which is a behavior change for the fifteen other callers: a unit with no config of its own beside a root anchor folds into the root. It was not audited per detector beyond reading each gate. Not verified: no test, typecheck or lint was run.

### MkDocs Detector

- **Problem:** The MkDocs module in `detected-area-rules/documentation/` was an empty scaffold, so a repository documented with MkDocs emitted no `Documentation` area. `mkdocs.yml` is an exclusive filename, but in the research sample (1,227 repositories) 13.7% had it only in workflows, project templates, demos, test fixtures or vendored trees, and the shared documentation blocklist does not cover template, sample, `.github` or `{{` placeholder paths.
- **Solution:**
  1. Implemented `addMkDocsDocumentationAreas` on `applyDeclarativeAreaDetector` with five signals: `mkdocs.yml|yaml` scores 3 (the anchor, and the whole gate), `overrides/*.html` 2, and `docs/stylesheets|javascripts/`, `docs/index.md` and `.pages` 1 each. The gate is `has` the config alone, because requiring a companion would drop 15.7% of real repositories. The candidate has primary technology `MkDocs` and related technology `Python`; `'MkDocs'` was added to `DocumentationDetectedAreaTechnology`.
  2. Added `excludingMkDocsNonDocumentationFolders` to `documentation/non-documentation-folders.ts`: the shared list first, then MkDocs-only folder names and any `{{` placeholder. Every MkDocs schema uses it, so a fixture's support file cannot feed the real project's score or evidence. The shared list and the Sphinx detector are unchanged.
  3. Reused `resolveManifestDirectoryOwner` unchanged as the `ownerAdapter`, with `manifestDirectories` computed once from the shared config regex (the Helm pattern).
  4. Added `resolve-manifest-directory-owner.mkdocs.test.ts` (owner spec from real layouts: mkdocs-material, traefik, fmt, fastapi, google-apis-rs, backstage).
  5. Updated the dispatcher docblock to name MkDocs as implemented.
  6. Deleted `project-structure-detected-area-rules.test.ts` (2,394 lines: the same-owner claim, nested-host and Terraform, Helm, Ansible and AWS CDK detector cases) at the author's decision, because the file had grown large; a MkDocs detector block that had been added to it was removed with it. Nothing replaces that coverage, so the detector-level behavior of the other detectors and of MkDocs has no analyzer-level test.
- **Affected files:** `detected-area-rules/documentation/mkdocs-documentation-area-rules.ts`, `detected-area-rules/documentation/non-documentation-folders.ts`, `detected-area-rules/documentation/documentation-area-rules.ts` (docblock), `detected-area-rules/owner-adapters/resolve-manifest-directory-owner.mkdocs.test.ts` (new), `project-structure-detected-area-rules.test.ts` (deleted), `project-structure-analyzer.types.ts`, this README and changelog.
- **Outcome:** A repository with a non-excluded `mkdocs.yml` or `mkdocs.yaml` now emits a `Documentation` area with primary technology `MkDocs`, owned by the config folder (`.` for a root config, the shared parent for sibling configs, the workspace unit under `apps/` or `packages/`). In the research sample 1,059 of 1,227 repositories keep an anchor after the exclusions; that sample is search-biased, was tuned and checked on the same repositories with no held-out set, and the figures come from the research, not from running the TypeScript. The new owner spec uses hand-computed expectations and was not run, and typecheck and lint were not run. Known limitations are in the README's Risks & Mitigations: about 73% of detections resolve to the root, a config far from its pages resolves to the config folder, Zensical and other forks are labelled `MkDocs`, and there is no analyzer-level test for MkDocs or the exclusion regexes. Docusaurus has research but is not implemented.

## 2026-10-06

### Documentation Detected Area: Dispatcher, Sphinx Detector, and Sphinx Owner Adapter

- **Problem:** `'Documentation'` was a member of the `DetectedAreaName` union and the `sortPriority` orderings but had no dispatched detector, so a repository whose documentation is a Sphinx project emitted no area. `conf.py` is a generic name (settings modules, nginx or ceph configs, test fixtures), so on its own it is wrong about 42% of the time in the research sample. Test, demo and vendored folders hold most `conf.py` files (565 of 1,420), and the infrastructure-as-code demo/test list misses `demo`, word-style `test` folders such as `rtd_tests` and `test-resources`, and vendored names. No shared owner adapter fits: `resolveManifestDirectoryOwner` collapses sibling projects into their parent, which would merge unrelated Sphinx projects such as nova's `doc`, `api-ref` and `releasenotes`.
- **Solution:**
  1. Added `detected-area-rules/documentation/`: a dispatcher (`documentation-area-rules.ts`) wired last in `applyDetectedAreaRules`, after infrastructure as code, and twelve framework modules in expected-popularity order. Only Sphinx is implemented; MkDocs, Docusaurus, mdBook, Starlight, DocFX, Antora, Fumadocs, VitePress, VuePress, Dumi and Rspress are empty scaffolds that emit nothing.
  2. Implemented the Sphinx detector on `applyDeclarativeAreaDetector` with four signals: `conf.py` scores 2 (the anchor), an index file (`index.rst|md|txt`, `contents.rst|md|txt`, `index.rst.template`) 2, and `Makefile` and `.readthedocs.yml|yaml` 1 each. The gate is `hasAllOf` `conf.py` and an index file. `_static/` and `_templates/` were first included as a second companion and then dropped: beside an index file they add nothing (132 of 241 real projects have both), and alone they rescued 2 of 241. The candidate has primary technology `Sphinx` and related technology `Python`; `DocumentationDetectedAreaTechnology` was added to `DetectedAreaTechnology`.
  3. Added `excludingNonDocumentationFolders` (`documentation/non-documentation-folders.ts`), separate from the infrastructure-as-code helper so widening it cannot change the finished detectors. It rejects any directory segment that is a delimited `test` word, `demo`/`demos`, `example(s)`, `testdata`, `fixtures`, `spec`, or a vendored name (`vendor`, `third_party`, `3rdparty`, `external`, `extern`, `node_modules`, `site-packages`). Every Sphinx schema uses it.
  4. Added `deriveSphinxProjectDirectories`, computed once per repository: the folder of every non-blocked `conf.py` that has a direct-child index file (`.` for a root project, original case kept). The `conf.py` and index regexes are shared constants used by both the schemas and the derivation.
  5. Added `resolveSphinxProjectOwner({ path, projectDirectories })` (`owner-adapters/resolve-sphinx-project-owner.ts`, exported from the adapters barrel) and wired it as the detector's `ownerAdapter`. A project folder owns itself, except that a folder whose last segment is `source` is owned by its parent; a root owner owns every path; otherwise the shortest owner folder that holds the path wins, so nested projects fold into the enclosing one and siblings stay separate; a path no owner holds resolves to its own folder. The author wrote the function from the spec in `resolve-sphinx-project-owner.test.ts`, which was written first from real layouts (django, cpython, nova, sympy, pytorch) without reference to an implementation.
  6. Moved `parentOf` from `resolve-manifest-directory-owner.ts` to `project-structure-path-utils.ts` so both adapters import it from the shared utils (no behavior change for the manifest adapter).
  7. Archived the three oldest dated sections (2026-08-24, 2026-08-26, 2026-08-27) from this changelog into `changelog-archive.md`, because the active file was at 32 entries and 442 lines. The totals across both files are unchanged: 64 dated sections and 110 entries.
- **Affected files:** `detected-area-rules/documentation/` (new: dispatcher, `non-documentation-folders.ts`, Sphinx detector, eleven empty scaffolds), `detected-area-rules/owner-adapters/resolve-sphinx-project-owner.ts` (new), `detected-area-rules/owner-adapters/resolve-sphinx-project-owner.test.ts` (new), `detected-area-rules/owner-adapters/index.ts`, `detected-area-rules/owner-adapters/resolve-manifest-directory-owner.ts` (`parentOf` import only), `project-structure-path-utils.ts` (`parentOf`), `project-structure-analyzer.types.ts`, `project-structure-detected-area-rules.ts`, this README, changelog and `changelog-archive.md`.
- **Outcome:** A repository with a non-blocked `conf.py` and a direct-child index file in the same folder now emits a `Documentation` area with primary technology `Sphinx`, owned by that folder (the parent for a `source/` folder). In the research sample the gate kept 232 of 241 real projects (96.3%) and passed none of the 176 non-Sphinx files; that sample is search-biased, was tuned and checked on the same repositories with no held-out set, and the figures come from the research's own simulation, not from running the TypeScript. Known limitations, recorded in the README's Risks & Mitigations: no cap on owners (apache/airflow has 117), the workspace-unit rule is not applied, and a root `.readthedocs.yml` attaches only to a root project. The author reported `resolve-sphinx-project-owner.test.ts` passing; it was not re-run during the documentation reconciliation. There is no unit test for `deriveSphinxProjectDirectories` or the blocklist and no analyzer-level Sphinx case, and typecheck and lint were not run. Research for MkDocs and Docusaurus exists but neither is implemented.

## 2026-10-03

### CLI Tooling Detector Evaluated and Not Built

- **Problem:** `'CLI tooling'` is a member of the `DetectedAreaName` union and the three `sortPriority` orderings but has no dispatched detector. Before building one, the plan was to detect it from the most popular CLI libraries (commander, yargs, click, typer, clap). The analyzer is path-only and never reads file contents, so the open question was whether those libraries leave any path evidence.
- **Solution:** Research only; no detector, test or type was added.
  1. Read the documentation of commander, Click and clap. None prescribes a file or directory layout. The library is declared in `package.json` dependencies, `pyproject.toml` `[project.scripts]` or `Cargo.toml`, all of which are file contents.
  2. Surveyed 34 real repositories whose manifests were read to confirm the library (commander 8, yargs 6, click 8, typer 5, clap 7) against 10 non-CLI controls (web servers and Rails apps), using the GitHub tree API. `test`, `docs`, `examples`, `templates` and `vendor` folders were dropped before scoring.
  3. The library name appears in a path in at most one repository per library: 0 of 8 commander, 0 of 5 typer, and one each for yargs (a helper file in nx), clap (bat's `clap_app.rs`) and click (a false match on `on-click` in a spec filename). The generic signals do not separate libraries either: `bin/`, `cli.*`, `cli/` and `commands/` fire under all five, and `src/main.rs` and `__main__.py` separate only by language.
  4. As a test for "this repository is a CLI", the narrow set (`cli.*`, `cli/`, `commands/`) hit 13 of 22 repositories hand-tagged as primarily CLI tools and 4 of 10 controls. The broad set (adding `bin/`, `src/main.rs`, `src/bin/`, `__main__.py`, `cmd/<name>/main.go`) hit all 22 but also 8 of 10 controls: Rails `bin/dev`, `src/main.rs` in Lemmy and realworld-axum, and `cmd/app/main.go` in go-clean-template. The 12 libraries and frameworks that merely ship a CLI (Playwright, Cypress, Jest, Flask, Celery and others) fire the same signals as real CLI tools.
- **Affected files:** None. The README rule, status checklist item and Risks & Mitigations row were updated to record the decision.
- **Outcome:** No `CLI tooling` detector was built, and the area name stays in the union and orderings but is never emitted, like `Shared package` and `Test suite`. Not validated: the oclif (`src/commands/`, `bin/run.js`), Cobra (`cmd/root.go`) and Laravel Zero (`app/Commands/`) layout fingerprints, because none of the sampled repositories used those frameworks. Reopen only if the path-only rule is relaxed (reading manifest contents needs its own ADR) or those three fingerprints are validated against real repositories. Caveats: the sample is small, the positives were chosen by hand and skew toward large well-known repositories, the controls were deliberately web servers (so 8 of 10 is not a real-world false-positive rate), and the CLI-primary tagging is the author's judgement. Five candidate repositories were dropped (Mocha, Stryker and langserve could not be confirmed from their manifests; ripgrep uses `lexopt`, not clap); Jest's yargs use was confirmed by hand. The survey script and data are not committed. No typecheck, lint or tests were run, since only documentation changed.

## 2026-10-02

### AWS CDK Detector

- **Problem:** The AWS CDK provider module under `detected-area-rules/infrastructure-as-code/` was an empty placeholder, so a repository whose infrastructure is AWS CDK emitted no `Infrastructure as code` area. CDK has a per-project anchor (`cdk.json`) like Pulumi's `Pulumi.yaml`, but its signal contract, gate and owner resolution had not been researched.
- **Solution:**
  1. Implemented the AWS CDK detector on `applyDeclarativeAreaDetector` with three signals: `cdk.json` scores 3 (the anchor, exclusive to AWS CDK), `cdk.context.json` 2, and `cdk.out/manifest.json` 1. The gate is `cdk.json` alone, because the two supports add up to exactly the emission floor of 3; requiring a support file as well lost 143 of 712 emitting repositories, and a second anchor on `cdk.out/manifest.json` gained 7 clones of one tutorial. Conventional stack files, `bin/*.ts`, `app.py`, `cdktf.json`, `cdk8s.yaml`, `sst.config.ts` and `amplify/backend.ts` are deliberately unscored. Every schema reuses the shared demo/test exclusion. The candidate has primary technology `AWS CDK` and related technology `AWS`.
  2. Wired the shared `resolveManifestDirectoryOwner` as the detector's `ownerAdapter` with the directory of every counted `cdk.json`, computed once per call from a regex constant shared with the config schema; the adapter itself is unchanged. On 579 single-project repositories it found the project folder in 575, against 354 for the default resolver, 418 for the Terraform and Bicep folder lists and 579 for the unit-root resolver, which was rejected for producing 5,550 areas against 2,892.
  3. Added `resolve-manifest-directory-owner.aws-cdk.test.ts`: grouped `it.each` cases from real repositories with hand-written directory lists, whose expected owners were decided from each repository's layout, one known gap pinned with `it.fails.each` (a workspace container hiding the project folder), and two `it.todo` for undecided layouts. Added an `AWS CDK infrastructure as code detector` block to `project-structure-detected-area-rules.test.ts` that runs the detector end to end, including that support files alone never emit and that a support file outside its project is dropped.
  4. Updated the infrastructure-as-code dispatcher docblock, the `InfrastructureAsCodeDetectedAreaTechnology` docblock and the shared adapter's docblock, and added an amendment note to [ADR 0008](adr/0008-shared-manifest-directory-owner-adapter.md) for the fourth adapter user.
- **Affected files:** `detected-area-rules/infrastructure-as-code/aws-cdk-infrastructure-as-code-area-rules.ts`, `detected-area-rules/infrastructure-as-code/infrastructure-as-code-area-rules.ts` (docblock), `project-structure-analyzer.types.ts` (docblock), `detected-area-rules/owner-adapters/resolve-manifest-directory-owner.ts` (docblock), `detected-area-rules/owner-adapters/resolve-manifest-directory-owner.aws-cdk.test.ts` (new), `project-structure-detected-area-rules.test.ts` (AWS CDK block added).
- **Outcome:** A repository with any counted `cdk.json` now emits an `Infrastructure as code` area with primary technology `AWS CDK`, owned by its project folder, with nested projects folded into their enclosing project and sibling projects into their parent; it coexists with a Terraform, Helm, Bicep, Pulumi or Ansible candidate on the same owner. All six v1 infrastructure-as-code providers now emit. Known limitations, recorded in the README's Risks & Mitigations: a workspace container hides the project folder (4 of 579 single-project repositories), sample collections under unlisted folder names still emit (49 of 712 repositories), and repositories that run CDK without a `cdk.json` emit nothing. The survey figures (975 repositories, 712 with a counted `cdk.json`) come from a search-biased draw tuned and checked on the same repositories; the owner comparison ran the repository's real resolvers on cached trees, the survey data is not committed, and the new specs have not been run.

### Ansible Detector

- **Problem:** The Ansible provider module under `detected-area-rules/infrastructure-as-code/` was an empty placeholder, so a repository whose infrastructure is Ansible emitted no `Infrastructure as code` area. Ansible has no single file whose folder is the project (Helm has `Chart.yaml`, Pulumi has `Pulumi.yaml`), and in a survey of 876 repositories 121 of the 515 that emit keep Ansible in a subfolder (97 of them in a folder named `ansible`), which the engine's default owner resolution puts at `.`.
- **Solution:**
  1. Implemented the Ansible detector on `applyDeclarativeAreaDetector` with eight signals: four exclusive anchors that score 3 (`ansible.cfg`, `tasks/main.yml`, anything inside `group_vars/` or `host_vars/`, `galaxy.yml`), `.ansible-lint` and `molecule/<scenario>/molecule.yml` at 2, and `handlers|defaults|meta|vars/main.yml` and `site.yml`, `playbook.yml` or `playbooks/*.yml` at 1. The gate is `hasOneOf` the four anchors, because requiring two lost 204 of 515 emitting repositories. Every schema rejects `.github/` and keeps the shared demo/test exclusion; `ansible.cfg` also rejects any `etc/` segment (the system-wide config) and `galaxy.yml` rejects a `*.info` parent folder (install metadata). Primary technology is `Ansible` with no related technology.
  2. Added `deriveManifestDirectories`, computed once per repository: the folder of `ansible.cfg` or `galaxy.yml`; for `tasks/main.yml` the folder above the first `roles/` segment, or above `tasks/` for a standalone role; for `group_vars/` or `host_vars/` the folder above the earliest of the first `roles/`, `inventory`/`inventories` and the variables folder. It keeps original case, because the engine passes the adapter original-case paths. The four anchor regexes are shared constants used by both the schemas and the derivation. `molecule/` is not used: it would have added a directory for 5 paths in 4 of 133 repositories with a molecule scenario.
  3. Wired the shared `resolveManifestDirectoryOwner` as the detector's `ownerAdapter` with that list; the adapter itself is unchanged.
  4. Added `resolve-manifest-directory-owner.ansible.test.ts`: grouped `it.each` cases from real repositories with hand-written directory lists, whose expected owners were decided from each repository's layout, and two `it.todo` for undecided layouts. Added an `Ansible infrastructure as code detector` block to `project-structure-detected-area-rules.test.ts` that runs the detector end to end: seven cases for the derived owner (a standalone role, a root `galaxy.yml`, a root `inventory/`, `inventory/<env>/` and roles in one folder, vendored roles, original case, a `my-roles` folder) and four cases that emit nothing (support signals alone, `etc/`, a `*.info` metadata file, demo/test folders).
  5. Updated the infrastructure-as-code dispatcher docblock and the `InfrastructureAsCodeDetectedAreaTechnology` docblock, and added an amendment note to [ADR 0008](adr/0008-shared-manifest-directory-owner-adapter.md) for the third adapter user.
- **Affected files:** `detected-area-rules/infrastructure-as-code/ansible-infrastructure-as-code-area-rules.ts`, `detected-area-rules/infrastructure-as-code/infrastructure-as-code-area-rules.ts` (docblock), `project-structure-analyzer.types.ts` (docblock), `detected-area-rules/owner-adapters/resolve-manifest-directory-owner.ansible.test.ts` (new), `project-structure-detected-area-rules.test.ts` (Ansible block added)
- **Outcome:** A repository with any counted Ansible anchor now emits an `Infrastructure as code` area with primary technology `Ansible`, owned by the project folder derived from its anchors, with nested projects folded into the enclosing one and sibling projects into their parent; it coexists with a Terraform, Helm, Bicep or Pulumi candidate on the same owner. The survey figures (515 of 876 repositories emit, 636 areas, 49 of 51 role and collection repositories found, 1 of 188 unrelated-topic repositories emits and it is a real Ansible repository) come from Python replicas of an earlier variant of the detector, not from running the TypeScript. Known limitations, recorded in the README's Risks table: free-form playbook-only repositories emit nothing, Ansible tool repositories emit, sibling folding merges unrelated projects, and the contract comes from a search-biased survey tuned and checked on the same repositories. Tests were not run, so neither the new resolver spec nor the new analyzer-level Ansible cases (which are the only coverage of `deriveManifestDirectories`) are confirmed to pass.

## 2026-10-01

### Pulumi Detector and Shared Manifest-Directory Owner Adapter

- **Problem:** The Pulumi provider module under `detected-area-rules/infrastructure-as-code/` was an empty placeholder, so a repository whose infrastructure is Pulumi emitted no `Infrastructure as code` area. Pulumi has a per-project anchor (`Pulumi.yaml`) like Helm's `Chart.yaml`, and a survey of 448 repositories showed the Helm resolver's shape was the right one: the generic resolver found the project folder in 83 of 191 single-project repositories, the Terraform folder-name lists in 141, `resolveUnitRootOwner` in all 191 but with 3,317 areas (five template, example and documentation repositories produced 2,097 of them), and the Helm-shaped resolver in 190 with 1,365. Copying the Helm resolver would have duplicated rules that have to stay identical.
- **Solution:**
  1. Implemented the Pulumi detector on `applyDeclarativeAreaDetector`: `Pulumi.yaml` scores 3 (the anchor, so one file clears the gate) and `Pulumi.<stack>.yaml` 2; the gate is `pulumi-project-file` alone, because requiring a stack file lost 91 of 289 emitting repositories to remove 5 tool repositories. Only `.yaml` is matched, since `Pulumi.yml` is used by 2 of 372 repositories with a project file and lowercased `pulumi.yml` scanner rules and CI workflows cannot be told from it. The project-file regex rejects `.github/` and the empty provider stubs under root `sdk/<language>/` and `provider/{cmd,pkg,test-programs}/` (48 repositories), and every schema keeps the shared demo/test exclusion. The directory of every counted `Pulumi.yaml` is computed once per repository. Primary technology is `Pulumi` with no related technology.
  2. Replaced `resolveHelmChartOwner` with `resolveManifestDirectoryOwner({ path, manifestDirectories })` (`owner-adapters/resolve-manifest-directory-owner.ts`, exported from the adapters barrel) and deleted `resolve-helm-chart-owner.ts`. The rules and their order are unchanged: a workspace unit first, then a root manifest, then the shortest enclosing manifest directory with sibling folding, then an orphan's own directory. ## 2026-09-16

### React Native Owner Resolution: Path-Shape Fallback for Unanchored Example Apps

- **Problem:** Widened research past the 2026-09-14 entry's six repositories surfaced a real-repo gap the 2026-09-14 owner wiring did not anticipate: `software-mansion/react-native-screens`' `FabricExample/` and `TVOSExample/`, and `react-native-picker/picker`'s `FabricExample/`, are complete, independently-native RN example apps with no `react-native.config.js` of their own, so no `anchorOwners` entry encloses their evidence. `android-native-shell`, `ios-native-shell`, and `metro-bundler-config` matches for these apps fell through to `ownerPathForApplicationArea`'s directory-name allowlist, which does not (and structurally cannot) recognize an arbitrary example-app directory name it was never told about, and returned the repository root -- silently swallowing a fully separate app into whatever other owner the repository's one recognized anchor happened to produce.
- **Solution:**
  1. Added two new fallback branches to the shared `resolveUnitRootOwner` (`detected-area-rules/owner-adapters/resolve-unit-root-owner.ts`), tried after the `anchorOwners` lookup finds no enclosing owner and before the generic `ownerPathForApplicationArea` call: a path containing an `android`/`ios` path segment resolves to everything before that segment; a path ending in `metro.config.(js|cjs|mjs|ts)` resolves to its own immediate parent directory. Both rely on the file-system conventions themselves (a native platform folder, Metro's own config-at-root contract) rather than a directory-name allowlist, so they generalize to any example-app directory name at any nesting depth.
  2. Both branches are unconditional -- not gated to React Native's signals or to `isAnchorSignal` -- since neither convention is React-Native-exclusive; any current or future caller of this shared resolver whose evidence takes one of these two path shapes benefits identically. Anchor-verified ownership still wins when available: both branches sit strictly after the `anchorOwners` lookup, never before it.
  3. Restored `return parts.slice(0, -1).join('/');` as the anchor branch's fallthrough for any anchor signal that is not the `app/_layout` special case. This line had been present in the accepted 2026-09-14 state and was dropped during the same edit that introduced the two branches above; without it, every non-`app/_layout` anchor signal whose parent directory name `ownerPathForApplicationArea` does not recognize (e.g. a custom-named app root like `mobile/react-native.config.js`, already documented as a real shape in the 2026-09-14 research) would have fallen through to the same swallowing gap this entry otherwise fixes for non-anchor signals. This is a regression fix restoring the Decision section's original anchor-dirname rule, not a new architectural decision.
  4. Added 3 new cases to `resolve-unit-root-owner.react-native.test.ts` under the "an unrelated anchor elsewhere in the repo must not swallow a fully separate example app" block, each asserting `android-native-shell`, `ios-native-shell`, and `metro-bundler-config` evidence for `FabricExample`/`TVOSExample`/picker's `FabricExample` resolves to that app's own directory, not the repository root or a sibling anchor's owner.
  5. Documented the new mechanism in a 2026-09-16 [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md) update, and corrected the 2026-09-14 changelog entry's now-inaccurate "introducing no new resolver logic" and "resolveUnitRootOwner itself was not modified" claims in place, since that entry was still uncommitted (not yet accepted history) when this fix landed.
- **Affected files:** `detected-area-rules/owner-adapters/resolve-unit-root-owner.ts`, `detected-area-rules/owner-adapters/resolve-unit-root-owner.react-native.test.ts`, `adr/0003-pluggable-owner-adapters-anchor-signals.md`, this changelog (including an in-place correction of the 2026-09-14 entry above).
- **Outcome:** `android-native-shell`, `ios-native-shell`, and `metro-bundler-config` evidence for an unanchored example app now resolves to that app's own directory instead of the repository root or an unrelated sibling anchor's owner, for any directory name -- not limited to the three real repositories that motivated the fix. Not yet re-verified: the owner-adapter suite has not been re-run since these changes (the 2026-09-14 entry's 185-test run predates them), the `.react-native.test.ts` file's non-`.only` cases have not been confirmed passing in this session, and no analyzer-output fixture exercises this path end to end -- consistent with the existing Risks entry on rebuilding per-detector fixtures. ### Static Frontend and Express Migrated onto the Declarative Engine (Shared-Candidate-Map Veto Added)

- **Decision:** Add a `checkForExistingCandidate` flag to `applyDeclarativeAreaDetector` that vetoes an owner already claimed for the same detected area in the shared candidate map, then migrate the two detectors previously left hand-written solely for that reason (Static frontend, Express).
- **Problem:** The 2026-08-27 migration left Static frontend and Express permanently hand-written because each vetoes its own emission based on whether a stronger detector already claimed the same owner in the shared output candidate map (`hasAreaCandidate`), not on raw repository file evidence. `applyDeclarativeAreaDetector` only supported `competingProofSchemas`, which re-scans the repository file index and has no mechanism to query emitted-candidate state. Both detectors' shape gates were otherwise already expressible as nested `ConditionShape` (OR-of-AND with at most two nested OR-groups per node).
- **Solution:**
  1. Added `checkForExistingCandidate?: boolean` to `applyDeclarativeAreaDetector`. When `true`, the per-owner loop skips any owner for which `hasAreaCandidate({ candidates, name: detectedArea, path: ownerPath })` is already true, before the `competingProofSchemas` and `gateBlocker` checks; it is evaluated independently of `competingProofSchemas`. Default (unset) behavior is unchanged for the 20 already-migrated detectors.
  2. Migrated `addStaticFrontendAreas` (`detected-area-rules/frontend/static-frontend-area-rules.ts`) onto `applyDeclarativeAreaDetector` with `checkForExistingCandidate: true`; translated `hasStaticContentShape`'s four-branch boolean gate (root index+CSS, index+`css/` directory stylesheet, multi-page HTML+any CSS, index+`src/` CSS+Vite config) into a four-branch `ConditionShape` and removed the hand-written finder blocks, `countAreaRuleSignal` loops, and helper.
  3. Migrated `addExpressBackendAreas` (`detected-area-rules/backend/express-backend-area-rules.ts`) the same way; translated `hasExpressBackendShape`'s three-branch gate (generator shape, layered API shape, server-owned API shape) into a three-branch `ConditionShape` and removed `hasExpressBackendShape`. The layered-API branch uses one `hasOneOf` group plus one `or` group in a single node, within the documented two-OR-group-per-node capacity.
  4. Updated the `applyDeclarativeAreaDetector` docstring to document `checkForExistingCandidate`, and replaced the two migrated detectors' docstrings that referenced the now-removed hand-written helpers.
- **Affected files:** `apps/backend/src/services/github-analysis/project-structure/detected-area-rules/declarative-area-rule-engine.ts`, `detected-area-rules/frontend/static-frontend-area-rules.ts`, `detected-area-rules/backend/express-backend-area-rules.ts`, this README and changelog.
- **Outcome:** 22 of the real framework/database/containerization/test detectors are now pure declarative config; only ASP.NET Core (per-entry exclusion predicate) and React (two independent OR-of-AND groups ANDed in one gate node) remain permanently hand-written. ### Laravel, Rails, and Spring Boot Migrated onto the Declarative Engine (Related-Tech Primitive Added)

- **Decision:** Add a `dynamicRelatedTechMap` primitive to `applyDeclarativeAreaDetector` instead of a general per-owner related-tech callback, then migrate the three detectors previously left hand-written solely because of dynamic related technology (Spring Boot, Laravel, Rails).
- **Problem:** The 2026-08-27 migration left Spring Boot, Laravel, and Rails permanently hand-written because none could declare related technology that depends on which files were actually matched (Blade/ERB view presence, Java/Kotlin source extension) -- `applyDeclarativeAreaDetector` only supported a static `relatedTechs` array. Laravel and Rails already had a discrete, unambiguous signal for the conditional case (`laravel-blade-view`, `rails-erb-view`); Spring Boot's six source-file signals (main application, web controller, REST resource, data repository, service, configuration class) each matched both `.java` and `.kt` under one signal type, so no counted signal could distinguish the language.
- **Solution:**
  1. Added `dynamicRelatedTechMap?: Partial<Record<Signal, DetectedAreaTechnology>>` to `applyDeclarativeAreaDetector`: for every signal counted for an owner that has an entry in the map, its technology is unioned into that owner's related technologies alongside any static `relatedTechs`.
  2. Migrated `addLaravelBackendAreas` and `addRailsBackendAreas` onto `applyDeclarativeAreaDetector` with signal shape unchanged -- `dynamicRelatedTechMap: { 'laravel-blade-view': 'Blade' }` and `{ 'rails-erb-view': 'ERB' }` replace the hand-written `hasBladeView`/`hasErbView` ternaries; their gates translate directly to nested `ConditionShape` with no new engine surface.
  3. Split each of Spring Boot's six language-ambiguous signals into `-java`/`-kotlin` variants (e.g. `spring-boot-main-application` becomes `spring-boot-main-application-java`/`-kotlin`), each scored identically to the original unsplit signal, and mapped all twelve split signals to `Java`/`Kotlin` in `dynamicRelatedTechMap`. Migrated `addSpringBootBackendAreas` onto `applyDeclarativeAreaDetector`, translating `hasSpringBootBackendShape`'s three-branch boolean gate into a four-branch `ConditionShape` (one branch needed splitting into two because it ANDs three independent OR-groups together, one more than a single `ConditionShape` node's `hasOneOf`+`or` capacity absorbs). Removed `hasSpringBootBackendShape`, `addLanguageEvidence`, and the parallel `springBootLanguagesByOwner` map entirely.
  4. Corrected the `applyDeclarativeAreaDetector` docstring, which did not mention `dynamicRelatedTechMap`.
- **Affected files:** `apps/backend/src/services/github-analysis/project-structure/detected-area-rules/declarative-area-rule-engine.ts`, `detected-area-rules/backend/laravel-backend-area-rules.ts`, `detected-area-rules/backend/rails-backend-area-rules.ts`, `detected-area-rules/backend/spring-boot-backend-area-rules.ts`, this README and changelog.
- **Outcome:** 20 of the real framework/database/containerization/test detectors are now pure declarative config; only ASP.NET Core, React, Static frontend, and Express remain hand-written, for reasons unrelated to related technology (a per-entry exclusion predicate, a two-independent-OR-groups condition in one gate node, and gating on the shared candidate map instead of raw file evidence). An owner with both a Java file and a Kotlin file in the same Spring Boot signal category (e.g. one Java controller and one Kotlin controller) now scores that category's points twice instead of once, since the two extensions are now distinct signal types -- a minor, accepted scoring change limited to mixed-language owners. Typecheck/lint/tests were not run as part of this change.

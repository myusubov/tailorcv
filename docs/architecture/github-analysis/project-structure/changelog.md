## 2026-09-18

### Flutter Mobile Detected-Area Detector

- **Problem:** `addFlutterMobileAreas` had been left as a side-effect-free scaffold since the 2026-09-12 Mobile app category implementation (empty `signalScores`/`entrySchemas`), so no repository ever produced a `Mobile app` area from Flutter evidence, and the Android/iOS overlap risk flagged in the 2026-09-12 entry's Risks note had no detector to actually collide with yet.
- **Solution:**
  1. Surveyed ten real repositories (flutter/samples, krille-chan/fluffychat, cake-tech/cake_wallet, invoiceninja/admin-portal, immich-app/immich, ente-io/ente, AppFlowy-IO/AppFlowy, cypherstack/stack_wallet) plus dart-lang/http and dart-lang/args as plain-Dart negative controls via the GitHub tree API, published as a standalone research artifact ("Flutter Signal Survey") before implementation.
  2. Implemented `addFlutterMobileAreas` (`detected-area-rules/mobile/flutter-mobile-area-rules.ts`) on `applyDeclarativeAreaDetector`: two anchors (`flutter-metadata` / `.metadata`, `flutter-pubspec-manifest` / `pubspec.yaml`) and six supportive signals (`flutter-ios-platform-dir`, `flutter-macos-platform-dir`, `flutter-desktop-cmake`, `flutter-entrypoint` / `lib/main.dart`, `flutter-android-splash` / the `launch_background.xml` splash drawable, `flutter-integration-test-dir` / `integration_test/`). Researched and dropped `.fvmrc`/`.fvm/` (Flutter Version Management): real and zero-false-positive in-sample, but present in only 1 of 8 sampled repos and feeding no `dynamicRelatedTechMap` entry, so not worth the surface yet.
  3. Designed a 3-branch gate mirroring React Native's with-config/without-config split: (A) `flutter-metadata` plus `flutter-pubspec-manifest` -- the clean, complete unit; (B) `flutter-metadata` plus one platform-directory signal -- covers `cypherstack/stack_wallet`'s confirmed real case, where `pubspec.yaml` is gitignored and generated at build time from a template but `.metadata` survives; (C) `flutter-pubspec-manifest` plus one platform-directory signal -- the symmetric, unobserved hedge for a team that scrubs `.metadata` but keeps the manifest. `pubspec.yaml` alone was never trusted, the same reasoning Expo's gate already applies to `app.config.ts` against Nuxt 3 -- it's Dart's manifest, not Flutter's, and every plain-Dart package in both control repos has one too.
  4. Wired `ownerAdapter: (args) => resolveUnitRootOwner({ ...args, extraRootDirectories: ['example'] })` -- the eighteenth detector on this adapter, and the first to introduce zero new adapter logic of any kind: both anchors sit at the plain unit root, and the non-anchor `flutter-ios-platform-dir`/`flutter-android-splash` signals already ride the 2026-09-16 `android`/`ios` path-segment fallback unchanged. No `competingProofSchemas`: Flutter shares no file-level signals with Expo or React Native. Documented in a 2026-09-18 [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md) update.
  5. Widened the owner-resolution research specifically for this detector past the original ten-repository signal survey, hunting real monorepo/library shapes the way the React Native owner-resolution spec's own citations do: `flutter/packages` (Google's own federated-plugin monorepo -- a 6-sibling `camera` family, each with its own `example/` app; `.metadata` inconsistently committed at plugin roots but not their `example/` apps; a plain-Dart `camera_platform_interface` sibling; a `test_apps/a11y_assessments` demo app under a non-`example` naming convention; a `.ci/legacy_project/all_packages/` CI-only fixture app; two version-named sibling examples under `google_maps_flutter_web`; an unrelated, content-verified plain-Dart CLI tool's `pubspec.yaml` five segments deep; an orphaned root-level `.metadata` with no accompanying app scaffold) and `fluttercommunity/plus_plugins` (a melos workspace whose root `pubspec.yaml` is a workspace manifest, not an app). Added `resolve-unit-root-owner.flutter.test.ts` (asserted directly against `resolveUnitRootOwner`, without inspecting `flutter-mobile-area-rules.ts` while writing it, to avoid designing test fixtures around the implementation rather than independent evidence).
  6. This research surfaced, without fixing, a property of the shared `anchorOwners` non-anchor branch: its `path === owner || path.startsWith(owner + '/')` check can never match an owner of `'.'`, since no real path is ever the literal string `.` or starts with `./`. The fix that would close this (matching `'.'` unconditionally) was traced by hand and rejected: it breaks an existing, real, confirmed case in `resolve-unit-root-owner.react-native.test.ts` (`software-mansion/react-native-screens`' `FabricExample/`) by short-circuiting the `android`/`ios` fallback that currently produces the correct answer there. Documented as an unresolved, evidence-symmetric ambiguity in a 2026-09-18 [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md) update rather than patched either direction.
  7. Updated `mobile-area-rules.ts`'s dispatcher docstring to record the agreed direction for the still-scaffolded Android and iOS detectors: once they have their own signal research, each should carry a `competingProofSchemas` veto against Flutter's and React Native's anchors, the same shape React Native already uses against Expo, so Flutter's/React Native's bundled native host directories don't also double-fire as a native Android/iOS app. Not implemented here, since neither Android nor iOS has signals of its own yet to attach a veto to.
  8. Reconciled this README's key-files table, component/module tree, section 6.5 owner-resolution and Mobile app dispatch rules, Implementation Status, and Risks & Mitigations; updated `adr/README.md`.
- **Affected files:** `detected-area-rules/mobile/flutter-mobile-area-rules.ts`, `detected-area-rules/mobile/mobile-area-rules.ts`, `detected-area-rules/owner-adapters/resolve-unit-root-owner.flutter.test.ts` (new), `adr/0003-pluggable-owner-adapters-anchor-signals.md`, `adr/README.md`, this README and changelog.
- **Outcome:** `Mobile app` areas now emit for repositories committing recognizable Flutter evidence, including the confirmed gitignored-manifest case. Android and iOS remain undetected scaffolds. No analyzer-output fixture exercises the new gate -- consistent with every other implemented detector in this domain, not a gap unique to Flutter; see the existing Risks entry on rebuilding per-detector fixtures. `resolve-unit-root-owner.flutter.test.ts`'s expected values were verified by hand-tracing `resolveUnitRootOwner`'s logic against each case, not by running the suite. Typecheck, lint, and tests were not run as part of this change.

## 2026-09-16

### React Native Owner Resolution: Path-Shape Fallback for Unanchored Example Apps

- **Problem:** Widened research past the 2026-09-14 entry's six repositories surfaced a real-repo gap the 2026-09-14 owner wiring did not anticipate: `software-mansion/react-native-screens`' `FabricExample/` and `TVOSExample/`, and `react-native-picker/picker`'s `FabricExample/`, are complete, independently-native RN example apps with no `react-native.config.js` of their own, so no `anchorOwners` entry encloses their evidence. `android-native-shell`, `ios-native-shell`, and `metro-bundler-config` matches for these apps fell through to `ownerPathForApplicationArea`'s directory-name allowlist, which does not (and structurally cannot) recognize an arbitrary example-app directory name it was never told about, and returned the repository root -- silently swallowing a fully separate app into whatever other owner the repository's one recognized anchor happened to produce.
- **Solution:**
  1. Added two new fallback branches to the shared `resolveUnitRootOwner` (`detected-area-rules/owner-adapters/resolve-unit-root-owner.ts`), tried after the `anchorOwners` lookup finds no enclosing owner and before the generic `ownerPathForApplicationArea` call: a path containing an `android`/`ios` path segment resolves to everything before that segment; a path ending in `metro.config.(js|cjs|mjs|ts)` resolves to its own immediate parent directory. Both rely on the file-system conventions themselves (a native platform folder, Metro's own config-at-root contract) rather than a directory-name allowlist, so they generalize to any example-app directory name at any nesting depth.
  2. Both branches are unconditional -- not gated to React Native's signals or to `isAnchorSignal` -- since neither convention is React-Native-exclusive; any current or future caller of this shared resolver whose evidence takes one of these two path shapes benefits identically. Anchor-verified ownership still wins when available: both branches sit strictly after the `anchorOwners` lookup, never before it.
  3. Restored `return parts.slice(0, -1).join('/');` as the anchor branch's fallthrough for any anchor signal that is not the `app/_layout` special case. This line had been present in the accepted 2026-09-14 state and was dropped during the same edit that introduced the two branches above; without it, every non-`app/_layout` anchor signal whose parent directory name `ownerPathForApplicationArea` does not recognize (e.g. a custom-named app root like `mobile/react-native.config.js`, already documented as a real shape in the 2026-09-14 research) would have fallen through to the same swallowing gap this entry otherwise fixes for non-anchor signals. This is a regression fix restoring the Decision section's original anchor-dirname rule, not a new architectural decision.
  4. Added 3 new cases to `resolve-unit-root-owner.react-native.test.ts` under the "an unrelated anchor elsewhere in the repo must not swallow a fully separate example app" block, each asserting `android-native-shell`, `ios-native-shell`, and `metro-bundler-config` evidence for `FabricExample`/`TVOSExample`/picker's `FabricExample` resolves to that app's own directory, not the repository root or a sibling anchor's owner.
  5. Documented the new mechanism in a 2026-09-16 [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md) update, and corrected the 2026-09-14 changelog entry's now-inaccurate "introducing no new resolver logic" and "resolveUnitRootOwner itself was not modified" claims in place, since that entry was still uncommitted (not yet accepted history) when this fix landed.
- **Affected files:** `detected-area-rules/owner-adapters/resolve-unit-root-owner.ts`, `detected-area-rules/owner-adapters/resolve-unit-root-owner.react-native.test.ts`, `adr/0003-pluggable-owner-adapters-anchor-signals.md`, this changelog (including an in-place correction of the 2026-09-14 entry above).
- **Outcome:** `android-native-shell`, `ios-native-shell`, and `metro-bundler-config` evidence for an unanchored example app now resolves to that app's own directory instead of the repository root or an unrelated sibling anchor's owner, for any directory name -- not limited to the three real repositories that motivated the fix. The restored anchor-dirname fallthrough closes the same swallowing gap for non-`app/_layout` anchor signals with an unrecognized parent directory name. Not yet re-verified: the owner-adapter suite has not been re-run since these changes (the 2026-09-14 entry's 185-test run predates them), the `.react-native.test.ts` file's non-`.only` cases have not been confirmed passing in this session, and no analyzer-output fixture exercises this path end to end -- consistent with the existing Risks entry on rebuilding per-detector fixtures. Typecheck, lint, and the broader backend test suite were not run as part of this change.

## 2026-09-14

### React Native (Bare CLI) Detected-Area Detector

- **Problem:** `addReactNativeMobileAreas` had been left as a side-effect-free scaffold since the 2026-09-12 Mobile app category implementation (empty `signalScores`/`entrySchemas`), so no repository ever produced a `Mobile app` area from bare React Native CLI evidence, and an owner that individually installs Expo SDK modules without adopting Expo Router had no detector path to being flagged as React Native either.
- **Solution:**
  1. Researched the official `react-native-community/template` scaffold plus six real production repositories (Mattermost, Expensify, Zulip, Rainbow, Gutenberg Mobile, Ledger Live) and a ~13k-hit GitHub code search for `react-native.config.js`, published as an artifact ("React Native Flight Book") before implementation.
  2. Implemented `addReactNativeMobileAreas` (`detected-area-rules/mobile/react-native-mobile-area-rules.ts`) on `applyDeclarativeAreaDetector`: one anchor (`react-native-cli-config` / `react-native.config.js`) and four supportive signals (`android-native-shell` / `android/{build.gradle,settings.gradle,gradlew}`, `ios-native-shell` / `ios/Podfile`, `react-native-application-bootstrap` / `android/app/src/main/{java,kotlin}/**/MainApplication.{java,kt}`, `metro-bundler-config` / `metro.config.js`), plus a sixth, zero-scored `expo-modules-coexistence` signal (`app.config.(ts|js)`, `eas.json`) used only by `dynamicRelatedTechMap`, never the gate.
  3. Designed a 3-branch gate -- (A) config file plus at least one native corroborator, (B) both native platform shells with no config file needed, (C) the Android bootstrap class plus the iOS shell -- so repositories scaffolded after `react-native.config.js` dropped out of the official template still clear. Researched and rejected two weak tiebreakers (`.watchmanconfig`, `app.json`) after confirming `AREA_CONFIDENCE_MAX_SCORE` (6) is already saturated by every gate-passing branch's required signals alone, so neither could move confidence or the `MIN_AREA_SCORE` floor.
  4. Added a `competingProofSchemas` veto against Expo's `expo-router-root-layout` (`app/_layout.*`) and `expo-router-typed-env` (`expo-env.d.ts`) file shapes, deliberately excluding the weaker `app.config.*`/`app.json`/`eas.json` shapes: a rainbow-me/rainbow case study (its `package.json` content, read for research only -- the detector itself stays path-only) showed a real, large, bare React Native wallet app legitimately carrying `app.config.ts` because it individually installs Expo SDK modules (`expo-image-picker`, `expo-web-browser`, etc.) via the `install-expo-modules` pattern, without Expo Router or the managed workflow. Added `dynamicRelatedTechMap: { 'expo-modules-coexistence': 'Expo' }` so that weaker coexistence evidence is surfaced in `related` instead of silently dropped or wrongly vetoing a real React Native repository.
  5. Wired `ownerAdapter: (args) => resolveUnitRootOwner({ ...args, extraRootDirectories: ['example'] })` -- the seventeenth detector on this adapter. The anchor itself sits at the unit root with no below-the-root stripping, unlike Expo's `app/_layout.*`, and `extraRootDirectories: ['example']` is reused unchanged for the same library-demo-app convention observed in RN native-module libraries (react-native-webview and peers). Documented in a 2026-09-14 [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md) update. (See the 2026-09-16 entry below: this detector's non-anchor signals turned out to need new resolver logic after all.)
  6. Updated `mobile-area-rules.ts`'s dispatcher docstring: the `competingProofSchemas` veto, not Expo's dispatch-order precedence, is what actually prevents a double-primary Expo/React Native claim on the same owner.
  7. Reconciled this README's key-files table, section 6.5 owner-resolution and Mobile app dispatch rules, Implementation Status, and Risks & Mitigations; updated `adr/README.md`.
- **Affected files:** `detected-area-rules/mobile/react-native-mobile-area-rules.ts`, `detected-area-rules/mobile/mobile-area-rules.ts`, `adr/0003-pluggable-owner-adapters-anchor-signals.md`, `adr/README.md`, this README and changelog.
- **Outcome:** `Mobile app` areas now emit for repositories committing recognizable bare React Native CLI evidence, with an Expo-Router/typed-env owner vetoed outright and weaker Expo-adjacent evidence (`app.config.*`/`eas.json`) surfaced as a related technology instead of silently dropped. Flutter, Android, and iOS remain undetected scaffolds. No analyzer-output fixture exercises the new gate, veto, or hedge -- consistent with every other implemented detector in this domain (Expo included), not a gap unique to React Native; see the existing Risks entry on rebuilding per-detector fixtures. `npx tsc --noEmit` was run against the backend and passed clean (exit 0), and the existing owner-adapter suite (`resolve-unit-root-owner.test.ts`, `resolve-unit-root-owner.expo.test.ts`, `resolve-container-root-owner.test.ts`, `resolve-container-root-owner.podman-oci.test.ts` -- 185 tests) was run and passed against `resolveUnitRootOwner` as it stood at this point, before the 2026-09-16 entry's fallback branches were added. Lint and the broader backend test suite were not run.

## 2026-09-12

### Mobile App Detected-Area Category (Expo Implemented)

- **Problem:** `'Mobile app'` had been a placeholder in the `DetectedAreaName` union (like `'CI/CD workflows'` before its 2026-09-11 implementation) but had no dispatched detector, so no repository ever produced a `Mobile app` area regardless of how much Expo, React Native, Flutter, or native Android/iOS evidence it committed.
- **Solution:**
  1. Added `MobileDetectedAreaTechnology` (`Android`, `Expo`, `Flutter`, `iOS`, `React Native`) and `Dart`/`Swift` to `RuntimeDetectedAreaTechnology`, unioned into `DetectedAreaTechnology`, in `project-structure-analyzer.types.ts`.
  2. Added `detected-area-rules/mobile/mobile-area-rules.ts`, dispatching Expo, then React Native, then Flutter, Android, and iOS -- the meta-framework (Expo, built on React Native) before its parent framework, followed by the remaining independent platforms -- and wired `addMobileAreas` into `project-structure-detected-area-rules.ts` as the last call in `applyDetectedAreaRules`, after CI/CD.
  3. Implemented `addExpoMobileAreas` (`detected-area-rules/mobile/expo-mobile-area-rules.ts`) on `applyDeclarativeAreaDetector`, based on a GitHub code-search sample of ~90 real repositories: three anchor signals (`expo-router-typed-env` / `expo-env.d.ts`, `expo-dynamic-config` / `app.config.(ts|js)`, `expo-router-root-layout` / `app/_layout.*`) and three supportive signals (`metro-bundler-config` / `metro.config.js`, `eas-build-config` / `eas.json`, `expo-static-config` / `app.json`). The sample found a real collision -- Nuxt 3 ships an identically named, identically placed `app.config.ts` -- so the gate requires at least one anchor and never lets a lone anchor clear alone: it must pair with a second anchor or a supportive signal.
  4. Extended `resolveUnitRootOwner` (`detected-area-rules/owner-adapters/`) with a dedicated rule for `expo-router-root-layout`'s nested anchor shape (stripping the matched `app/_layout.*` suffix and any enclosing `src` segment instead of taking the plain dirname, since the file sits one or two directories inside its actual project root) and an optional `extraRootDirectories` parameter forwarded to the non-anchor fallback, so Expo can pass `['example']` for the `create-expo-module` library-demo-app convention without widening the shared `MONOREPO_OWNER_ROOT_DIRECTORIES` for every other caller. Wired `ownerAdapter: (args) => resolveUnitRootOwner({ ...args, extraRootDirectories: ['example'] })` onto the Expo detector -- the sixteenth detector on this adapter.
  5. Added `resolve-unit-root-owner.expo.test.ts` (16 cases) covering the co-located anchors as regression guards, all four `app/_layout` shape combinations (root/monorepo x plain-`app`/`src`-`app`, plus an extension-variant sweep) as the new rule's target behavior, and the supportive-signal nearest-enclosing-anchor and fallback paths.
  6. Left `addReactNativeMobileAreas`, `addFlutterMobileAreas`, `addAndroidMobileAreas`, and `addIosMobileAreas` as side-effect-free scaffolds (empty `signalScores`/`entrySchemas`, so `applyDeclarativeAreaDetector` matches nothing and adds no candidates) wired into dispatch but with no matching, scoring, or emission logic implemented yet.
  7. Added a 2026-09-12 update section to [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md) documenting Expo as the sixteenth detector on `resolveUnitRootOwner` and the first whose anchor sits below (not at) the unit root; updated `adr/README.md`. No new ADR was created for the category itself, matching the CI/CD precedent -- the gate is the engine's existing `hasOneOf`/`hasAllOf`/`or`/`and` primitives with no novel precision-vs-recall tradeoff.
  8. Reconciled this README's key-files table, component/module tree, section 6.5 owner-resolution and Mobile app dispatch rules, Implementation Status, and Risks & Mitigations.
- **Affected files:** `project-structure-analyzer.types.ts`, `project-structure-detected-area-rules.ts`, `detected-area-rules/mobile/mobile-area-rules.ts` (new), `detected-area-rules/mobile/{expo,react-native,flutter,android,ios}-mobile-area-rules.ts` (new), `detected-area-rules/owner-adapters/resolve-unit-root-owner.ts`, `detected-area-rules/owner-adapters/resolve-unit-root-owner.expo.test.ts` (new), `adr/0003-pluggable-owner-adapters-anchor-signals.md`, `adr/README.md`, this README and changelog.

## 2026-09-11

### CI/CD Workflows Detected-Area Category

- **Problem:** `'CI/CD workflows'` had been a placeholder in the `DetectedAreaName` union since its addition alongside `'Test suite'` (2026-08-24) but had no dispatched detector, so no repository ever produced a `CI/CD workflows` area regardless of how many pipeline config files it committed.
- **Solution:**
  1. Added `CiCdDetectedAreaTechnology` (`AppVeyor`, `Azure Pipelines`, `Bitbucket Pipelines`, `Buildkite`, `CircleCI`, `Drone CI`, `GitHub Actions`, `GitLab CI/CD`, `Jenkins`, `TeamCity`, `Travis CI`, `Woodpecker CI`) to the `DetectedAreaTechnology` union in `project-structure-analyzer.types.ts`.
  2. Implemented eleven single-purpose provider detectors under `detected-area-rules/ci-cd/`, each built on `applyDeclarativeAreaDetector` with no new engine capability: GitHub Actions (`.github/workflows/*.yml`, decisive; `.github/actions/*/action.yml`, support-only), GitLab CI/CD (`.gitlab-ci.yml`, decisive; `.gitlab/ci/**`, support-only), CircleCI (`.circleci/config.yml`, decisive; `.circleci/src/**`/`continue_config.yml`, support-only), Jenkins (`Jenkinsfile` at any depth, the sole anchor and only per-directory owner), Azure Pipelines (`azure-pipelines*.yml`/`.azure-pipelines/`/`build/azure-pipelines/`, decisive; `eng/pipelines/**`, support-only), Buildkite (`.buildkite/pipeline.yml`/`buildkite.yml`, decisive; `.buildkite/pipelines/**`, support-only), Travis CI (`.travis.yml`, sole signal), Bitbucket Pipelines (`bitbucket-pipelines.yml`, sole signal), Drone CI/Woodpecker CI (`.drone.yml`/`.woodpecker.yml`/`.woodpecker/*`, sole signal, shared primary label `Drone CI`), AppVeyor (`appveyor.yml`/`.appveyor.yml`, sole signal, root-anchored specifically to reject vendored copies such as `vendor/k8s.io/**/appveyor.yml`), and TeamCity (`.teamcity/settings.kts`+`pom.xml` or `.teamcity/**/project-config.xml`, either decisive; `buildTypes/`/`vcsRoots/` files, support-only).
  3. Ten of the eleven pass no `ownerAdapter` and resolve to the repository root through the generic resolver (every provider's config format is read only from a fixed root location). Jenkins is the exception: it passes `isAnchorSignal: true` plus `ownerAdapter: resolveUnitRootOwner` on its single signal, so each matched `Jenkinsfile` resolves to its own containing directory -- the only CI/CD provider, and the only detector on this adapter overall, that can emit more than one `CI/CD workflows` candidate for one repository (multibranch, per-service pipelines). Jenkins's regex also excludes `test/`, `tests/`, `fixtures/`, `examples/`, and the vendored set, since an any-depth match has no root-position guarantee the other ten providers get for free.
  4. Added `detected-area-rules/ci-cd/ci-cd-area-rules.ts`, dispatching all eleven in a fixed precedence order (GitHub Actions, GitLab CI/CD, CircleCI, Jenkins, Azure Pipelines, Buildkite, Travis CI, Bitbucket Pipelines, Drone/Woodpecker CI, AppVeyor, TeamCity) and wired `addCiCdAreas` into `project-structure-detected-area-rules.ts` as the last call in `applyDetectedAreaRules`, after containerization.
  5. Left three shapes deliberately undetected, each documented in its detector's own docstring rather than treated as a follow-up: Azure Pipelines' per-directory `<dir>/ci.yml` convention (the azure-sdk ~150-pipeline pattern) has no reliable path-only corroboration; GitLab's Settings -> CI/CD custom config-path override is invisible from the tree; TeamCity/Buildkite/AppVeyor pipelines are commonly configured entirely through each provider's UI with nothing committed to the repository.
  6. Added a 2026-09-11 update section to [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md) documenting Jenkins as the fifteenth detector on `resolveUnitRootOwner` and the first to anchor on a signal with no fixed unit-root position; updated `adr/README.md`. No new ADR was created for the category itself -- unlike the Containerization detectors (ADR 0001/0002), every CI/CD provider's gate is a single-decisive-signal-or-corroborating-support pattern already covered by the engine's existing `gateBlocker`/`hasOneOf` primitives, with no precision-vs-recall tradeoff novel enough to need its own durable decision record.
  7. Reconciled this README's key-files table, component/module tree, section 6.5 owner-resolution and CI/CD dispatch rules, and Implementation Status.
- **Affected files:** `project-structure-analyzer.types.ts`, `project-structure-detected-area-rules.ts`, `detected-area-rules/ci-cd/ci-cd-area-rules.ts` (new), `detected-area-rules/ci-cd/{github-actions,gitlab,circleci,jenkins,azure-pipelines,buildkite,travis,bitbucket,drone-woodpecker,appveyor,teamcity}-ci-cd-area-rules.ts` (new), `adr/0003-pluggable-owner-adapters-anchor-signals.md`, `adr/README.md`, this README and changelog.
- **Outcome:** `CI/CD workflows` areas now emit for repositories committing recognizable pipeline-as-code for any of the eleven implemented providers, with Jenkins alone able to split per multibranch/per-service pipeline. `'CI/CD workflows'` is no longer an unused placeholder in the `DetectedAreaName` union. No analyzer-output fixture exercises the new detectors yet -- only `project-structure-detected-area-candidates.test.ts`, the `resolve-unit-root-owner`/`resolve-container-root-owner` specs, and `declarative-area-rule-engine.test.ts` retain unit coverage in this domain (see the existing Risks entry on rebuilding per-detector fixtures). Typecheck, lint, and tests were not run as part of this change.

## 2026-09-10

### Podman/OCI Containerization Owner Resolution via `resolveContainerRootOwner`

- **Decision:** Resolve Podman/OCI containerization owners through the same non-anchor `resolveContainerRootOwner` adapter the Docker detector uses ([ADR 0004](adr/0004-containerization-owner-resolution.md)), extended with a Quadlet/`Containerfile` basename matcher and a Podman-specific infra denylist, rather than the generic `ownerPathForApplicationArea`. `quadlet/` and `quadlets/` become containerization collection roots; `containers/` stays a non-unit folder because its `containers/systemd/` deploy-mirror role outweighs the rarer `containers/<image>/Containerfile` collection shape. This reverses "Podman/OCI is untouched and still uses the generic resolver only" from ADR 0004 and the 2026-08-24 amendment on [ADR 0002](adr/0002-podman-oci-containerization-gate.md).
- **Problem:** The Podman/OCI detector keyed candidates by `ownerPathForApplicationArea`, which recognizes only `apps/`, `packages/`, `libs/`, `services/`, `modules/` and the `src` boundary. - **Solution:**
  1. Added `PODMAN_OCI_CONTAINER_FILE_NAME` to `resolve-container-root-owner.ts` -- Quadlet unit extensions (`.container`, `.pod`, `.kube`, `.build`, `.image`, `.network`, `.volume`, `.artifact`), `Containerfile` and suffixed variants, and `.containerignore` -- mirroring the Podman/OCI signal regexes in `podman-oci-containerization-area-rules.ts`.

  3. Added `quadlet` and `quadlets` to `CONTAINER_DEPLOYMENT_ROOT_DIRECTORIES`, so `quadlet/<svc>/<file>` resolves to `quadlet/<svc>` through `ownerPathForApplicationArea` while a two-segment `quadlet/<file>` falls to `.` through the denylist -- the dual role `apps/` already has.
  4. Extended `resolveContainerRootOwner`'s two-segment branch: a name matching `PODMAN_OCI_CONTAINER_FILE_NAME` resolves to its directory unless that directory is in `PODMAN_OCI_NON_UNIT_TOP_LEVEL_DIRECTORIES`, in which case `.`. Paths two or more directories deep delegate to `ownerPathForApplicationArea` unchanged.
  5. Wired `ownerAdapter: ({ path }) => resolveContainerRootOwner(path)` onto the Podman/OCI detector in `podman-oci-containerization-area-rules.ts` (no `isAnchorSignal` schema, so the engine calls it once per matched entry), importing from the `owner-adapters` barrel.
  6. Added `resolve-container-root-owner.podman-oci.test.ts` with cases lifted verbatim from the scanned repositories (root-level units, `containers/systemd/` mirrors, single-app wrapper folders, flat homelab service directories, `quadlet`/`quadlets` collection roots, deeper-nesting stability, OCI `Containerfile` build directories, a monorepo regression guard, and judgment calls). `containers/ldap/Containerfile -> containers/ldap` is an `it.fails` case: `containers/` cannot become a collection root without breaking `containers/systemd/`.
  7. Added a 2026-09-10 update section to [ADR 0004](adr/0004-containerization-owner-resolution.md); amended [ADR 0002](adr/0002-podman-oci-containerization-gate.md) and [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md); updated `adr/README.md`; reconciled the README key-files table, component tree, section 6.5 owner-resolution and Podman/OCI rules, Implementation Status, and Risks & Mitigations; reconciled the docstrings in the two source files.

### Containerization Owner Resolution via `resolveContainerRootOwner`

- **Decision:** Resolve Docker containerization owners through a dedicated non-anchor `ownerAdapter`, `resolveContainerRootOwner`, and widen the shared generic `ownerPathForApplicationArea` rather than route every detector through the wider rules. This carves containerization out of [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md)'s "generic resolver only" statement; recorded as [ADR 0004](adr/0004-containerization-owner-resolution.md).
- **Problem:** After the 2026-08-24 consolidation, Docker evidence resolved through `ownerPathForApplicationArea`, which recognized only `apps/<name>` and `packages/<name>` plus the `src` boundary. A recursive tree scan of 466 container-file paths across 36 well-known repositories (next.js, nx, turborepo, cal.com, immich, n8n, posthog, backstage, airflow, dagger, zitadel, budibase, langfuse, supabase, grafana, and more) showed three unhandled shapes: real deployable units under `libs/`, `services/`, `modules/`, `products/` (posthog), `plugins/` (backstage), `providers/` (airflow); scoped npm packages collapsing to the bare scope folder (`packages/@n8n/benchmark` -> `packages/@n8n`); and multi-image repos shipping separate images from bare top-level directories (`server/`, `web/`, `worker/`, `machine-learning/` in immich and langfuse) or from a container file one directory below the root, all collapsing to `.` so a three-image repo produced one `Containerization` area. Docker has no contract-located config file (`docker build -f` relocates the Dockerfile; compose/bake are searched from the working directory), so the anchor-signal mechanism from ADR 0003 does not apply.
- **Solution:**
  1. Added `detected-area-rules/owner-adapters/resolve-container-root-owner.ts`: a path with no directory segment resolves to `.`; a container file (case-insensitive `Dockerfile`/`*.dockerfile` variants, `.dockerignore`, Compose, Bake -- mirroring the Docker signal regexes) exactly one directory deep resolves to that directory unless it is in `NON_UNIT_TOP_LEVEL_DIRECTORIES` (the exported `MONOREPO_OWNER_ROOT_DIRECTORIES` and `products`/`plugins`/`providers`, plus infra/tooling/dev-env names: `docker`, `.devcontainer`, `.github`, `deploy`, `deployments`, `packaging`, `hosting`, ...), in which case `.`; every deeper path delegates to `ownerPathForApplicationArea` with `products`/`plugins`/`providers` passed as extra roots.
  2. Widened `ownerPathForApplicationArea` in `project-structure-path-utils.ts`: replaced the two `apps`/`packages` `if` blocks with an exported `MONOREPO_OWNER_ROOT_DIRECTORIES` array (`apps`, `packages`, `libs`, `services`, `modules` -- a superset of `project-shape-detector.ts`'s roots, and the source the container adapter's denylist is composed from); added an `@scope` branch that keeps one extra segment (`packages/@n8n/benchmark`); added an optional `extraRootDirectories` parameter and moved the function to a single object parameter.
  3. Wired `ownerAdapter: ({ path }) => resolveContainerRootOwner(path)` onto the Docker detector in `docker-containerization-area-rules.ts` with no `isAnchorSignal` schema, so the engine calls the adapter once per matched entry.
  4. Updated the three existing callers of `ownerPathForApplicationArea` (`project-structure-area-rule-candidates.ts` x2, `resolve-unit-root-owner.ts`) to the object-parameter signature.
  5. Added `resolve-container-root-owner.test.ts` with cases derived from the 36-repo scan (root, monorepo, deep-subdir, infra folders, `.devcontainer`, scoped packages, unrecognized roots, bare top-level units); the one unresolved shape -- cal.com's `apps/api/v2` versioned sub-service collapsing to `apps/api` -- is an `it.fails` case.
  6. Added [ADR 0004](adr/0004-containerization-owner-resolution.md); amended [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md) with a 2026-09-08 update section; reconciled the README key-files table, owner-resolution rules in section 6.5, the Docker per-detector rules, Implementation Status, and Risks & Mitigations.

- **Outcome:** Docker `Containerization` areas split per deployable unit in multi-image repos and attribute `products/`/`plugins/`/`providers/` and scoped-package units to their real owner. The anchored detectors' generic fallback also benefits from the wider workspace-root set and `@scope` depth. ### Owner Adapters Extended to Backend Frameworks and Schema Tools

- **Decision:** Apply the `ownerAdapter` / `isAnchorSignal` mechanism from [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md) to every detector whose framework or tool pins its unit root with a file that sits, by that tool's own contract, at the project root -- not only the Next.js and Nuxt frontend detectors. Detectors whose root marker is deprecated, has no fixed location, or sits below the unit root keep the generic resolver.
- **Problem:** ADR 0003 wired `resolveUnitRootOwner` into Next.js and Nuxt only and its Decision section scoped the adapter to "unit frameworks," so backend frameworks (Django `manage.py`, ASP.NET Core `*.csproj`, Laravel `artisan`), config-anchored frontend meta-frameworks (Angular `angular.json`, Astro `astro.config.*`, React Router `react-router.config.*`, SvelteKit `svelte.config.*`), and schema tools with a root config (Prisma, Drizzle, SQLAlchemy/Alembic, Sequelize, Knex) still resolved every signal through the generic `ownerPathForApplicationArea`. The 2026-08-24 consolidation had removed the per-database resolvers that previously handled this, and the schema tools -- unlike Nest and TypeORM -- keep their `config`, `models`, and `migrations` folders at the project root rather than under `src/`, so the generic `src`-boundary rule cannot regroup them.
- **Solution:**
  1. Added `isAnchorSignal: true` plus `ownerAdapter: resolveUnitRootOwner` to the Django (`manage.py`), ASP.NET Core (`*.csproj`), and Laravel (`artisan`) backend detectors and the Angular (`angular.json`), Astro (`astro.config.*`), React Router (`react-router.config.*`), and SvelteKit (`svelte.config.*`) frontend detectors.   3. Split Prisma's `prisma-config` schema into a root-level `prisma.config.*` anchor and a non-anchor `.config/prisma.*` match (one level below the project root, so it only feeds the gate and score), then wired `ownerAdapter` on the Prisma detector. When no `prisma.config.*` is present -- the pre-Prisma-7 bare `prisma/schema.prisma` convention -- every signal still falls back to the generic resolver.
  4. Left TypeORM, Spring Boot, Rails, standalone Svelte, Vue, and React on the generic resolver, each for a concrete reason: TypeORM's `ormconfig.*` is deprecated/removed and `data-source.ts` has no contract location; Spring Boot's `pom.xml`/`build.gradle` is a build-tool file, not Spring-specific, and its `src/main/**` layout is already grouped by the `src` boundary; Rails' `config/application.rb` and `bin/rails` sit below the unit root (unsupported by `resolveUnitRootOwner`'s one-segment anchor branch) and its engine dummy apps would false-positive; Vue, standalone Svelte, and React delegate layout to the build tool and have no framework-owned root config.
  5. Amended [ADR 0003](adr/0003-pluggable-owner-adapters-anchor-signals.md) with a dated section widening the adapter's scope and narrowing its "database detectors use the generic resolver only" statement; updated the README key-files table, the section 6.5 owner-resolution rules, the per-detector rules for the fourteen anchored detectors, Implementation Status, and Risks & Mitigations.
